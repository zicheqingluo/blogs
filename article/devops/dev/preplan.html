    预案平台

    子车轻罗 2022/6/18 SREdevops

    # 简介

    预案平台是一款保障业务高可用的应急管理系统，旨在提高应对突发事件的能力和效率。平台包含了多云架构下应急管理最佳实践，为公司提供全方位的预案管理、演练评估和应急响应支持。

    # 功能

    1. 预案管理
      1. 预案准入，准出，涉及到预案规范
      2. 预案工单，依据规范将预案编排标准化，自动化。
    2. 预案执行
      1. 预案执行的前提是预案编排，根据不同的预案类型进行编排配置
      2. 全局预案->场景预案->原子预案
    3. 预案备份
      1. 根据预案类型定时备份，以便预案复位使用
    4. 预案复位
      1. 可根据预案类型单独复位，也可一键全局复位
    5. 预案验收
      1. 预案执行后的检查，确保不遗漏
    6. 预案自检
      1. 每日定时执行测试预案，以便自动检查预案平台功能是否正常。
    7. 预案通知
      1. 发送预案执行信息到运维变更通知群。

    # 整体架构

    从实现视角看，预案平台可以划分为接入、预案管理、编排执行、验收通知和数据存储几个部分：Web 与 API 接收运维人员操作，核心服务负责预案、工单、编排、备份复位和自检等业务逻辑，执行引擎再通过原子预案适配层对接云厂商 DNS、DOH、业务切流接口和作业平台。

    流程图

    图中的服务划分更偏向职责分层，并不等同于实际部署拓扑。真正需要关注的是编排与执行之间的解耦：编排层决定“执行哪些预案、按什么顺序执行”，执行引擎只负责把具体动作分发给对应的原子执行器。

    # 模型

    # 预案类型

    • 原子预案：是预案执行的最小单位，根据预案类型分为以下几种
      • 域名预案：基于南北向域名切流，常态下双云解析，流量均分，故障时将故障云的解析改为可用云的解析，是当前使用最广泛的方案。
      • DOH预案：同域名解析，接了DOH的客户端优先通过DOH的获取解析，此时切域名预案无法将流量切走，故增加DOH预案，按照百分比切流。
      • 特征预案：部分业务自建了预案，通过调用业务提供的接口来执行多云切流
      • 作业预案：以脚本的方式执行，脚本通过作业平台来触发
    • 场景预案：主要是用作编排，分组，按照业务预单维度进行划分，场景预案可涵盖多种原子预案，一键执行。可用作故障演练或局部业务故障单独切流使用。
    • 全局预案：包含多种场景预案，可一键切流所有场景预案，主要用作公司级演练或单云故障使用。

    全局预案和场景预案负责组织与编排，真正调用外部系统执行动作的是原子预案。

    # 域名模型

    因公司域名数量众多，云厂商接口有API限流，为满足3分钟内完成全公司切流的目标，我们将业务域名模型定义为三层解析，第一层是网关层，以云为单位，第二层为预单域名，以业务线为单位，第三次为产品域名，配置域名预案时，配置预单域名，这样数量就控制在200个以内，大大减少了执行时间。

    在这个基础上，全局预案负责公司级切流，场景预案按业务线组织，原子预案负责真正的执行动作。故障应急、故障演练和定时自检虽然是不同的触发方式，最终都会落到同一条“编排 → 执行 → 验收 → 复位”的链路上。

    # 关键流程

    # 预案生命周期

    一条预案从创建到可执行，需要先经过准入规范检查和工单编排；执行完成后，还要完成验收、复位和通知。完整生命周期如下图所示。

    准入负责把不规范的配置挡在执行之前，工单把一次变更涉及的原子预案、场景预案和全局预案组织起来，定时备份则为后续复位保留状态基线。准入审批、工单状态流转和异常处理的具体规则，最终仍要以平台配置为准。

    # 预案执行

    执行时，预案平台先加载预案配置和编排关系，再由执行引擎遍历待执行的原子预案。域名、DOH、特征和作业四类原子预案分别调用不同的外部接口，执行完成后逐级验收并发送通知。

    这里的关键不只是把接口调通，而是把执行状态、外部返回和验收结果统一记录下来。否则切流完成后，很难判断哪些动作已经生效、哪些还需要人工确认。

    # 备份与复位

    复位依赖定时备份。平台先保存切流前的配置快照，复位时读取对应快照恢复，而不是简单地把切流动作反向执行一遍。

    因此，备份不是附属功能，而是复位正确性的前提。按预案类型保存快照后，单项复位和全局一键复位才有稳定的状态依据。

    # 域名切流

    域名模型决定大规模切流时的执行效率。实际切流时，平台操作的是业务预单域名，而不是逐个修改产品域名；每个预单域名通过云厂商 DNS API 调整解析目标或权重，再查询实际配置完成验收。

    这样既把操作对象控制在 200 个以内，也降低了云厂商 API 限流对整体切流时间的影响。3 分钟是平台侧的切流目标，实际业务流量是否完成切换，还需要结合 DNS 生效和业务验证判断。

    # 每日自检

    预案自检用于验证平台自身是否可用，而不是验证某一次业务切流。平台每日加载测试预案，走一遍执行引擎和测试原子预案，检查结果后再记录或告警。

    这样可以在真实故障发生前发现编排、执行器或外部接口的失效，避免预案只在演练时才暴露问题。

    # 小结

    预案平台的价值不只是“把切流脚本搬到页面上”，而是把预案准入、编排、备份、执行、验收和复位串成可重复的闭环。三级预案模型解决“切什么”，原子执行器解决“怎么切”，三层域名模型解决“切得够不够快”，而备份复位和每日自检则保证这条链路在故障前后都能被验证。
